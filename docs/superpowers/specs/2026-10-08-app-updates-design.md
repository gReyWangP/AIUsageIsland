# 应用内更新接入方案

## 用户目标

在现有 AI Usage Island 中提供“检查更新”入口，可在应用内查看新版说明、下载并安装，不需要用户到 GitHub 手动下载。提供定期自动检查能力，但默认关闭；用户明确开启后才进行后台检查。源码保持私有，安装包和更新信息通过现有公开分发仓库发布。

## 用户体验

在“设置 → 通用与支持”增加“软件更新”区域：

- 当前版本。
- “检查更新”按钮。检查期间禁用重复提交；没有新版、网络失败、签名错误分别显示相应结果。
- “自动检查更新”开关，首次默认关闭。开启后使用 Sparkle 的定期检查；关闭后停止定期检查，手动按钮继续可用。
- 更新说明与下载/安装确认使用 Sparkle 标准界面。后台发现新版也需要用户确认，不默认静默下载或安装。

明确设置 Sparkle 的关闭默认值，避免第二次启动自行询问开启自动检查。保存用户后来选择的开启或关闭状态，不在每次启动覆盖。点击检查前让更新窗口正常置前，避免被现有悬浮设置窗口遮挡。

首次接入更新能力的版本需要手动安装一次；1.19.14 本身没有更新组件，不能自行升级。之后接入后的版本可通过应用内更新。

## 技术接入

使用 Sparkle 2 的稳定版本，并锁定 SwiftPM 依赖及解析结果。通过独立的 MainActor 更新服务包装 SPUStandardUpdaterController，向设置界面提供检查可用状态和自动检查偏好。更新服务随应用生命周期创建并保留，不依附于账号、登录、用量刷新或历史存储。

Sparkle 自己持久化自动检查偏好。Info.plist 明确将 SUEnableAutomaticChecks 和 SUAutomaticallyUpdate 默认设为 false。不在启动时调用属性设置覆盖已经保存的用户选择；也不额外维护第二份相同偏好。手动检查只从用户操作触发，后台检查交由 Sparkle 自己调度。

SwiftPM 开发和测试环境不自动启动生产更新服务。更新界面的行为通过可注入的更新后端验证；真实安装包使用真实 Sparkle 服务。

## 分发与更新信任

现有仓库：

- 私有源码：https://github.com/gReyWangP/AIUsageIsland
- 公开分发：https://github.com/gReyWangP/AIUsageIsland-releases

公开分发仓库保存 appcast.xml，应用从公开 HTTPS 地址读取更新清单。清单引用 GitHub Releases 的 ZIP 资产，并使用递增的 CFBundleVersion 判断版本。下载地址、长度、版本和 Sparkle Ed25519 签名由发布脚本生成，不手工填写。

使用 Sparkle 官方工具生成更新签名密钥，私钥保存在本机登录钥匙串，只有公钥写入应用的 Info.plist。私钥不上传任何仓库，不写入公开发布文件或日志。每个更新包都使用此密钥签名并验证。

当前本机没有 Developer ID 签名身份。接入更新功能不会宣称应用完成 Apple 公证；应用包签名与 Sparkle 更新包签名分别处理。现有临时签名包的检查、下载及替换路径需要真实安装验收，不能仅靠编译判断可用。

## 打包与发布

调整现有构建脚本，把 Sparkle.framework、必需的辅助程序、资源和许可证完整装入应用，保留符号链接与执行权限，设置正确的运行时库路径。按本地或正式构建模式对必要组件签名，并扩充应用验证脚本检查框架、嵌套签名和更新配置。

第一次发布接入版本时，先完成包构建与验证，再生成 ZIP 和签名清单；确认 GitHub 资产完整上传后再发布更新清单。发布标题和说明以功能、变化及安装方式为主，不包含测试数量或“测试版”文案。源码和私钥不能进入公开分发仓库。

## 验证与验收

自动化验证覆盖：默认关闭、用户选择跨启动保留、关闭后仍可手动检查、重复检查抑制、错误状态、缺失框架或配置时构建失败并保留已有包。运行完整项目测试及 Release 构建。

验证实际包中的 Sparkle 运行时路径、嵌套签名、公开清单格式、版本/长度/签名与发布资产一致性。使用隔离的安装副本和独立数据目录验证检查、下载和版本替换，避免修改用户现有应用或真实账号数据。验收无法完成的部分明确记录，不把模拟测试等同于实际升级成功。

最终交付：接入后的应用安装包、私有源码提交、公开发布与可用的签名更新清单，以及后续版本可复用的发布步骤。
